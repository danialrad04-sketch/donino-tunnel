# نصب دو سرور از پنل ایران

در این حالت، پنل ایران کنترل‌کنندهٔ نصب است. ایران به‌صورت محلی و با سرویس root جداگانه نصب می‌شود؛ خارج با OpenSSH، کلید اختصاصی کنترل‌کننده و host key تأییدشده مدیریت می‌شود. وب‌سرور همچنان با کاربر محدود `donino-link` اجرا می‌شود. API فقط عملیات ثابت ثبت اتصال، پیش‌نمایش، شروع و وضعیت را دارد؛ shell، فایل کلید خصوصی، مسیر نصب یا URL دانلود از مرورگر دریافت نمی‌شود.

## فعال‌سازی روی نصب موجود

نسخهٔ جدید باید روی ایران نصب شود. نصب‌کنندهٔ جدید در پایان نصب ایران سرویس `donino-control.service` را خودکار فعال می‌کند. روی نصب قدیمی که بسته‌اش را ارتقا داده‌ای:

```bash
sudo /opt/donino-link/current/venv/bin/donino-link control-enable
```

پنل را refresh کن و «راه‌اندازی خودکار» را باز کن. اگر کنترل‌کننده فعال نباشد، پنل این وضعیت را صریح نشان می‌دهد و دکمهٔ نصب نمی‌تواند موفقیت ساختگی گزارش کند.

## اتصال اولیهٔ خارج

برای نصب جدید [راهنمای دو پنل](role-setup.md) را دنبال کن: روی هر سرور `sudo bash scripts/setup.sh`، نقش ایران/خارج را انتخاب کن. در پنل خارج کد یک‌بارمصرف بساز و در پنل ایران همراه آدرس و پورت agent وارد کن. کپی کلید عمومی، دریافت fingerprint دستی و ویرایش authorized_keys لازم نیست. هویت TLS از کد تأیید می‌شود، سپس اثر انگشت SSH و کلید اختصاصی به‌صورت خودکار مبادله و login واقعی بررسی می‌شوند.

نصب قدیمی بدون پنل خارج هنوز در بخش بستهٔ «اتصال دستی به نصب قدیمی» پشتیبانی می‌شود: کلید عمومی اختصاصی ایران را فقط یک‌بار به SSH خارج بده و اثر انگشت `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` را از کنسول معتبر وارد کن. کلید خصوصی از پنل دریافت نمی‌شود. SSH همیشه `StrictHostKeyChecking=yes` و known_hosts اختصاصی دارد.

پیش‌فرض، مقصد SSH باید به IP عمومی resolve شود. برای شبکهٔ خصوصی VPC/LAN فقط اپراتور root می‌تواند روی ایران این حالت را فعال کند:

```bash
sudo /opt/donino-link/current/venv/bin/donino-link control-enable --allow-private-peers
sudo systemctl restart donino-control.service
```

## ساخت تانل

- اتصال ذخیره‌شدهٔ خارج، آدرس عمومی ایران و در صورت نیاز IP/دامنهٔ حامل خارج را انتخاب کن.
- یک یا چند پروتکل و سرویس TCP اضافه کن. مثال: `app`، ورودی `0.0.0.0:443` ایران، مقصد `127.0.0.1:8443` خارج. خود سرویس مقصد باید از قبل روی خارج اجرا شده باشد؛ پنل برنامهٔ VPN یا وب‌سرویس مقصد را نصب نمی‌کند.
- «نمایش نقشه» بسته‌های خصوصی هر دو node را می‌سازد. رمز، API token، آدرس و TLS هر دو پنل موجود حفظ می‌شوند؛ تغییر آدرس پنل در این فرم انجام نمی‌شود.
- پورت‌های لازمِ میزبان و provider را در نقشه بررسی و باز کن. گزینهٔ UFW فعال، فقط پورت‌های همین نصب را در پروفایل اختصاصی و قابل بازگشت باز می‌کند؛ UFW را روشن/خاموش نمی‌کند و default policy و SSH را تغییر نمی‌دهد. فایروال‌های میزبانِ دیگر و API شرکت میزبان در این نسخه خودکار تغییر نمی‌کنند. قواعد raw محدود و برچسب‌دار Paqet نیز خودکار مدیریت می‌شوند.
- پس از مرور نقشه، جایگزینی مجموعهٔ تانل‌ها را انتخاب کن و نصب را شروع کن. چند نصب هم‌زمان پذیرفته نمی‌شود. نقشه یک ساعت اعتبار دارد، فقط یک‌بار قابل اجراست و با تغییر تنظیمات فعال باطل می‌شود.

این عملیات **کل مجموعهٔ تانل‌های مدیریت‌شده** روی هر دو سرور را جایگزین می‌کند. برای حفظ یک مسیر آن را در انتخاب جدید هم نگه دار. اتصال‌های جاری ممکن است قطع شوند. رمز و آدرس پنل ثابت می‌مانند، ولی به‌دلیل restart دروازه باید دوباره login کنی. کار نصب با بستن مرورگر یا logout متوقف نمی‌شود؛ وضعیت پایدار روی سرور ذخیره می‌شود و بعد از ورود قابل مشاهده است.

## اصول نصب هر حامل

| حامل | ایران | خارج | پیش‌نیاز ویژه |
|---|---|---|---|
| FRP WSS | frps خصوصی و ورودی mTLS | frpc با CA و گواهی client | TCP حامل روی ایران |
| FRP QUIC | frps QUIC | frpc QUIC | UDP حامل روی ایران |
| BackPack WSS | server و گواهی TLS | client و token | مسیر آزمایشی؛ نسخهٔ ثابت manifest |
| Backhaul WSS | server و گواهی TLS | client و token | آزمایشی؛ محدودیت احراز هویت server |
| Paqet | KCP client و تشخیص NIC/MAC | KCP server و قواعد raw محدود | IPv4، CAP_NET_RAW/ADMIN، پورت اختصاصی |
| BrowserLink | Chromium و Node.js با sandbox | سایت HTTPS و WebSocket همان origin | ایران Debian 12/13، RAM حداقل ۱٫۵ GiB، اجازهٔ user/network namespace؛ آزمایشی |

نسخه‌های موتور و SHA256 از manifest خود پروژه گرفته می‌شوند؛ اسکریپت‌های نصب نامحدود پروژه‌های دیگر دانلود و اجرا نمی‌شوند. apt پیش‌نیازهای سیستم، venv بستهٔ Python و دانلودکننده باینری تأییدشده را نصب می‌کنند. دسترسی هر دو node به مخازن apt/PyPI/GitHub لازم است؛ شکست دانلود به‌عنوان خطای مرحله ثبت می‌شود. حالت نصب کاملاً آفلاین در این جریان هنوز پیاده نشده است.

## آماده‌سازی، فعال‌سازی و بازگشت

ابتدا هر دو node پیش‌نیازها، بسته، باینری‌ها، تنظیمات معتبر، شبکهٔ Paqet، فضای آزاد، پورت‌های اشغال‌شده و دسترسی TCP مقصد را بررسی می‌کنند. در این مرحله release فعال تغییر نمی‌کند، ولی بسته‌های apt و cache ممکن است اضافه شوند و در rollback حذف نمی‌شوند.

پس از آماده‌شدن هر دو، خارج و سپس ایران فعال می‌شوند. در صورت انتخاب UFW، فقط UFW فعال با app اختصاصی همان release تنظیم می‌شود؛ قواعد این app در rollback حذف و قواعد قبلیِ متعلق به Donino فقط پس از موفقیت بازنشسته می‌شوند. هر نقش پیش از تغییر دارای checkpoint پایدار است. سپس **تمام مسیرهای انتخاب‌شده** باید پاسخ تازه و امضاشده بدهند و تمام targetهای TCP در پاسخ سرور خارج reachable باشند. صرف start شدن systemd یا سلامت یک مسیر برای موفقیت کافی نیست. این بررسی، اتصال TCP مقصد و پیام سلامت حامل است؛ صحت پروتکل برنامهٔ دلخواه یا کیفیت شبکهٔ واقعی WAN را تضمین نمی‌کند.

در شکست پس از تغییر سرویس‌ها، بازگشت ایران و خارج با ترتیب معکوس اجرا می‌شود. guardِ release اجازه نمی‌دهد بازیابی دوباره یا بازیابی یک job قدیمی، نصب جدیدتر اپراتور را خراب کند. اگر کنترل‌کننده هنگام نصب از نو شروع شود، ابتدا journal را می‌خواند و تغییرات نیمه‌کاره را rollback می‌کند؛ نصبِ متوقف‌شده را موفق گزارش نمی‌کند. شکست SSH یا systemd هنگام rollback با وضعیت جداگانهٔ `rollback_failed` نمایش داده می‌شود و نیازمند بررسی اپراتور است.

## داده‌ها و خطایابی

- socket محلی: `/run/donino-control/control.sock`، مالک root و گروه donino-link، mode 660؛ endpoint شبکه‌ای عمومی برای worker وجود ندارد.
- کلید SSH، CA، plan و journal خصوصی: `/var/lib/donino-control` با mode 700؛ payload خارج فقط فایل‌های همان node را دارد و کلید CA یا credential مدیر را دریافت نمی‌کند.
- CA در حالت CLI قبلی آفلاین روی کنترل‌کننده بود؛ در حالت پنل، روی کنترل‌کنندهٔ ایران و تحت مالکیت root تولید و نگهداری می‌شود. CA به کاربر وب یا سرور خارج تحویل داده نمی‌شود.
- ۲۰ عملیات پایان‌یافتهٔ اخیر و آخرین plan موفق نگه داشته می‌شوند؛ پیش‌نمایش استفاده‌نشده بعد از یک ساعت پاک می‌شود.
- مراحل و نتیجهٔ probe برای مدیر در API قابل دیدن‌اند؛ خروجی کامل دستورات به دلیل احتمال رازهای موتور در log خصوصی root باقی می‌ماند.

```bash
sudo systemctl status donino-control.service
sudo journalctl -u donino-control.service --no-pager -n 100
sudo ls /var/lib/donino-control/jobs/
sudo cat /var/lib/donino-control/jobs/JOB_ID/private.log
```

نصب با HTTP طبق انتخاب صریح مدیر ممکن است؛ HTTP داده‌های مدیریتی و نشست را در شبکه رمزنگاری نمی‌کند. احراز هویت، CSRF و Origin check برای عملیات نصب هم فعال‌اند.

منابع اصول پیاده‌سازی: [UFW app profiles](https://manpages.ubuntu.com/manpages/bionic/man8/ufw.8.html)، [OpenSSH host key verification](https://man.openbsd.org/ssh-keyscan.1)، [FRP TLS/QUIC](https://gofrp.org/en/docs/features/common/network/network/)، [مستندات اصلی BackPack](https://github.com/AminMGMT/BackPack). پیکربندی اجرایی به نسخه‌های ثابت manifest و آزمون همان باینری‌ها محدود است؛ مستندات main می‌توانند با نسخهٔ ثابت فرق داشته باشند.

BrowserLink از namespace و seccomp sandbox استفاده می‌کند؛ چون سرویس `NoNewPrivileges` دارد، helper قدیمی setuid استفاده نمی‌شود. preflight اجازهٔ واقعی ایجاد namespace با کاربر محدود را بررسی می‌کند؛ سیاست kernel/AppArmor سرور تولیدی خودکار تضعیف نمی‌شود. آزمون container روی runner موقت Ubuntu، تنظیم user namespace همان میزبان آزمایشی را برای شبیه‌سازی Debian مجاز می‌کند.
