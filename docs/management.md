# مدیریت دو سرور بدون وابستگی به ورود SSH — ۰.۲.۱

خطای گزارش‌شدهٔ نصب قبلی `Permission denied (publickey,password)` بود. تنظیمات و fingerprint صحیح به‌تنهایی دلیل پذیرش کلید در تمام تلاش‌ها نیستند؛ برای علت قطعی رد شدن کلید، journal خود sshd لازم است. اصلاح این نسخه وابستگی نصب و تغییرات پنل به ورود root با SSH را از مسیر جفت‌سازی حذف می‌کند، بدون بازکردن ورود با رمز یا دستکاری کلیدهای شخصی مدیر.

## مسیر ارتباط

ایران یک کنترل‌کننده دارد؛ خارج یک agent محدود به عملیات مشخص. هر دو پنل عملیات محلی خودشان را دارند و پنل ایران می‌تواند نصب دوطرفه و کنترل مجاز خارج را انجام دهد. این ساختار به دسترسی shell متقابل و نامحدود دو پنل نیاز ندارد.

۱. کد یک‌بارمصرف خارج شامل pin کامل گواهی TLS و راز موقت است.
۲. ایران گواهی را پیش از ارسال HTTP تأیید می‌کند؛ redirect یا proxy محیطی استفاده نمی‌شود.
۳. خارج token اختصاصی، محدود به peer و IP مبدأ مشاهده‌شده می‌دهد؛ token خام فقط در فایل خصوصی ایران است و خارج digest آن را نگه می‌دارد.
۴. ایران challenge تصادفی می‌فرستد؛ خارج یک فایل ۰۶۰۰ موقت را می‌نویسد، fsync می‌کند، می‌خواند و حذف می‌کند. ایران hash پاسخ را تطبیق می‌دهد. این آزمون، data plane تانل یا امکان تغییر هر فایل دلخواه را ثابت نمی‌کند.
۵. نصب، کنترل سرویس، دریافت لاگ و ویرایش Paqet مجاز از HTTPS انجام می‌شوند. SSH برای اتصال‌های دستی قدیمی باقی مانده، اما در پروفایل جفت‌شده fallback به آن انجام نمی‌شود.

IP مبدأ در این نسخه ثابت فرض شده است. تغییر NAT، مسیر خروجی یا IP مبدأ می‌تواند احراز هویت را رد کند؛ برای مبدأ جدید، با کد جدید جفت کن. timeout شبکه، گواهی نامعتبر، پاسخ ۴۰۱ و نسخهٔ ناسازگار با هم اشتباه نمی‌شوند.

## ارتقای نصب موجود

ابتدا **خارج** و سپس **ایران** را ارتقا بده؛ روی هرکدام:

```bash
curl -fL --retry 3 --connect-timeout 15 https://raw.githubusercontent.com/danialrad04-sketch/donino-tunnel/main/install-donino.sh -o install-donino.sh && bash install-donino.sh --upgrade
```

نسخهٔ هر دو طرف:

```bash
/opt/donino-link/current/venv/bin/python -c 'from donino_link import __version__; print(__version__)'
```

سپس صفحه را reload کن. TCP پورت agent خارج، پیش‌فرض `9444`، باید از ایران در فایروال میزبان و provider در دسترس باشد. وجود ارتباط HTTPS مستقل از سلامت حامل‌هاست؛ داشتن یک Paqet سالم به‌تنهایی بازبودن این پورت را ثابت نمی‌کند.

در پنل ایران، صفحهٔ جفت‌سازی، سرور موجود را انتخاب و «آزمون ارتباط و دریافت سرویس‌های خارج» را اجرا کن. پروفایل قدیمی دارای token معتبر می‌تواند از کانال جدید استفاده کند؛ برای جفت‌سازی شکست‌خورده یا token ازدست‌رفته، در خارج کد تازه بساز و آن را در ایران وارد کن. کد قبلی مصرف‌شده را تکرار نکن.

نتیجهٔ مطلوب: نوشتن/خواندن تأییدشده، آمادگی root/systemd و runtime یکسان. ناسازگاری runtime اجازهٔ نصب تازه نمی‌دهد؛ هر دو طرف را با یک فایل نصب ارتقا بده. قابلیت مشاهده و کنترل موجود به نیاز ساخت v3 وابسته نیست.

## نصب داده‌محور و رسید عملیات

روی کانال مدیریت هیچ shell command، URL دانلود، مسیر دلخواه، فایل برنامه، archive یا unit دلخواهی از API پذیرفته نمی‌شود. ایران فقط spec و فایل‌های node را می‌فرستد. خارج با نسخهٔ نصب‌شدهٔ خودش plan مرجع می‌سازد و مجموعهٔ فایل‌ها، manifest، unitها و transport config را مقایسه می‌کند؛ تنها randomness کلیدهای ۳۲بایتی از مقایسهٔ قالب حذف می‌شود. هویت و کلیدهای leaf در نام‌های مشخص حمل می‌شوند؛ کلید امضای CA ارسال نمی‌شود.

پس از تأیید، خارج bundle برنامه را از **کد و installer محلی خودش** می‌سازد. یکسان‌بودن digest runtime پیش از این مرحله اجباری است. بنابراین از دسترسی HTTPS یک راه آپلود کد root ساخته نشده است. این اعتبارسنجی، ممیزی مستقل موتورهای upstream نیست.

هر prepare/activate/rollback یک رسید خصوصی با شناسهٔ peer، job، operation و hash درخواست دارد. تکرار همان درخواست، همان رسید را برمی‌گرداند؛ درخواست متفاوت با همان شناسه رد می‌شود. قطع پاسخ باعث اجرای دوباره نمی‌شود. عملیات پس از restart agent، `interrupted` ثبت می‌شود و کورکورانه تکرار نمی‌شود. کنترل‌کننده مرحلهٔ فعال‌سازی را پیش از اقدام journal می‌کند تا rollback محافظت‌شده روی release مورد انتظار ممکن باشد.

دو طرف قبل از فعال‌سازی آماده می‌شوند؛ تمام مسیرها و مقصدها بعد از فعال‌سازی آزموده می‌شوند. در شکست، rollback قبلی با release guard اجرا می‌شود. lease نصب، ویرایش دستی و نصب هم‌زمان را مسدود می‌کند. در قطع کامل کانال، rollback فوری خارج قابل تضمین نیست؛ وضعیت نامطمئن و رسید باید بررسی شود. هیچ معماری نرم‌افزاری بدون مسیر شبکه نمی‌تواند تغییر را فوراً به سرور قطع‌شده برساند.

## کنترل و تغییر تنظیمات

در بخش مدیریت خارج، ابتدا فهرست سرویس‌ها را دریافت کن. اسکن، سرویسی را فعال یا restart نمی‌کند. برای کنترل نصب بیرونی، «فعال‌کردن مدیریت این سرویس» لازم است. همان validation، redaction، revision guard، backup و rollback ویرایش محلی برای ویرایش مجاز خارج نیز استفاده می‌شود.

ویرایش یک Paqet بیرونی، تغییر خودکار طرف دیگر نیست. تغییر key، cipher، MTU یا قرارداد transport همچنان باید روی دو نقش هماهنگ باشد. فرم نصب مدیریت‌شده، هر دو نقش را با هم آماده و فعال می‌کند؛ فایل‌های نصب بیرونی بدون انتخاب مدیر به آن تبدیل نمی‌شوند.

لغو یک جفت، token و شواهد سلامت متعلق به آن را باطل می‌کند؛ حامل جاری و کلیدهای شخصی SSH مدیر حفظ می‌شوند. سرویس SSH میزبان از API مدیریت قابل توقف نیست. در جفت‌سازی HTTPS جدید، کلید root جدیدی در authorized_keys ثبت نمی‌شود. مجوزهای SSH متعلق به جفت‌های قدیمی، برای سازگاری باقی می‌مانند تا خود آن جفت لغو شود.

## اعتبارسنجی

- `tests/test_management.py`: TLS واقعی بین controller و agent محلی، pin اشتباه، token غلط، لغو، challenge واقعی فایل، کنترل سرویس، درخواست نصب با پاسخ ازدست‌رفته و جلوگیری از تکرار؛ همهٔ هشت transport از renderer محلی بازسازی می‌شوند. فراخوانی systemd در این تست محلی fixture است.
- `scripts/test-provision.py`: دو container واقعی systemd؛ ورود root در SSH پیش از جفت‌سازی ممنوع می‌شود. نصب، هشت حامل، حفظ پنل/رمز، rollback و لغو از مسیر HTTPS بررسی می‌شوند.
- آزمون شبکهٔ واقعی سرورهای کاربر جداست. موفقیت lab به معنی تأیید وضعیت زندهٔ ایران/خارج نیست.

این اصلاح مربوط به زیرساخت مدیریت است؛ تغییر پروتکل حمل ترافیک یا پیاده‌سازی Continuum v3 نیست.
