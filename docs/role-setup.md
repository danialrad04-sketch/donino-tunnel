# نصب ترمینالی و پنل مستقل هر سرور

همان اسکریپت روی **هر دو سرور** اجرا می‌شود. در شروع نقش را انتخاب می‌کنی؛ سپس آدرس همین سرور و رمز پنل دریافت می‌شوند. این مسیر به کنترل‌کنندهٔ سوم و کپی دستی کلید SSH نیاز ندارد.

## شروع

سرورها: Debian 12/13 یا Ubuntu 22.04 تا 26.04، amd64/arm64، systemd، دسترسی root و مخازن apt/GitHub. BrowserLink روی ایران به اجازهٔ واقعی namespace و sandbox کرنل نیاز دارد؛ نصب کامل هشت حامل حداقل ۱٫۵ GiB RAM می‌خواهد و برای بار واقعی باید ظرفیت جداگانه سنجیده شود.

در ترمینال root هر سرور، نصب را با یک فرمان شروع کن:

```bash
curl -fL --retry 3 https://raw.githubusercontent.com/danialrad04-sketch/donino-tunnel/main/install-donino.sh -o install-donino.sh && bash install-donino.sh
```

دریافت فایل به `curl` نیاز دارد. اگر فایل دریافت نشود، نصب اجرا نمی‌شود. نقش و آدرس از ترمینال دریافت می‌شوند؛ در صورت نصب قبلی، منوی ارتقا با حفظ تنظیمات نمایش داده می‌شود. اسکریپت فعال و enabled بودن پنل و سرویس مدیریت نقش را جداگانه بررسی و URL پنل را چاپ می‌کند.

روش دستی: فایل [install-donino.sh](../install-donino.sh) را با Download raw file از گیت‌هاب دریافت و **همان یک فایل** را روی هر دو سرور کپی کن. کد برنامه و فونت داخل فایل هستند؛ clone مخزن روی سرور لازم نیست. سپس:

```bash
sudo bash install-donino.sh
```

همهٔ گزینه‌های نصب، از جمله `--role`، `--address` و `--upgrade` برای این فایل هم قابل استفاده‌اند. وابستگی‌های Python داخل فایل هستند و به PyPI نیاز ندارند؛ دانلود apt و باینری‌های حامل انتخاب‌شده همچنان به اینترنت نیاز دارد. checksum داخلی، خرابی فایل همراه را بررسی می‌کند؛ فایل را از همین مخزن دریافت کن.

روش جایگزین برای کار با سورس: مخزن را clone کن یا پوشهٔ استخراج‌شده از Download ZIP گیت‌هاب را به هر سرور انتقال بده. در پوشهٔ پروژه، روی **هر سرور**:

```bash
sudo bash scripts/setup.sh
```

- `1`: ایران؛ پنل کنترل، انتخاب مسیرها و نصب هماهنگ دو سرور.
- `2`: خارج؛ پنل پایش، جفت‌سازی و کنترل واحدهای تانل.
- IP یا دامنهٔ عمومی **همین سرور** را وارد کن.
- رمز مدیر حداقل ۱۲ کاراکتر است؛ ورودی رمز در ترمینال نمایش داده نمی‌شود.

نصب بدون پرسش نقش و آدرس، ولی با دریافت امن رمز:

```bash
# روی ایران
sudo bash scripts/setup.sh --role iran --address IRAN_IP
# روی خارج
sudo bash scripts/setup.sh --role foreign --address FOREIGN_IP
```

اسکریپت URL واقعی پنل را چاپ می‌کند. پیش‌فرض:

| نقش | پنل HTTP | کانال جداگانهٔ جفت‌سازی |
|---|---|---|
| ایران | `http://IRAN_IP:8090` | کنترل‌کننده فقط socket محلی دارد |
| خارج | `http://FOREIGN_IP:8091` | TLS روی TCP `9444` |

پورت پنل با `--panel-port` و پورت agent خارج با `--agent-port` هنگام نصب اولیه قابل انتخاب است. پنل‌ها از ابتدا قابل ورودند، حتی وقتی هنوز هیچ تانلی نصب نشده است. این حالت صریحاً «هنوز پیکربندی نشده» نمایش داده می‌شود.

اگر UFW از قبل فعال باشد، تنها پروفایل محدود متعلق به همین نصب برای پورت‌های لازم ساخته می‌شود؛ UFW روشن/خاموش نمی‌شود. `--no-open-ufw` این تنظیم را نیز غیرفعال می‌کند. پورت‌های پنل، TCP `9444` خارج و سپس پورت‌های نقشهٔ تانل باید در فایروال شرکت میزبان نیز مجاز باشند. برای جفت‌سازی جدید، TCP کانال HTTPS خارج باید از ایران در دسترس باشد؛ SSH لازم نیست.

## نسخه‌های لینوکس

نصب اولیه و نصب دو سرور از یک تشخیص سیستم‌عامل استفاده می‌کنند. Debian 12/13 و همهٔ انتشارهای Ubuntu از 22.04 تا 26.04 روی amd64/arm64 پذیرفته می‌شوند؛ سرویس فعال systemd لازم است. نصب روی Fedora/RHEL/Alpine یا سیستم بدون systemd هنوز پیاده نشده است.

| نسخهٔ اوبونتو | پایتون سیستم | دریافت وابستگی‌ها |
|---|---|---|
| 22.04 | 3.10 | مخازن فعلی میزبان |
| 22.10، 23.04، 23.10 | 3.10/3.11 | آرشیو رسمی امضاشدهٔ Ubuntu |
| 24.04 | 3.12 | مخازن فعلی میزبان |
| 24.10، 25.04، 25.10 | 3.12/3.13 | آرشیو رسمی امضاشدهٔ Ubuntu |
| 26.04 | 3.14 | مخازن فعلی میزبان |
| 26.10 | پیش‌انتشار | تشخیص آماده؛ خارج از ماتریس تست انتشار پایدار |

نسخه‌های پایان پشتیبانی همچنان قابل نصب‌اند، ولی بسته‌های آرشیوی اصلاحات امنیتی جدید نمی‌گیرند. نصب‌گر برای آن‌ها فایل منبع اختصاصی خودش را می‌سازد؛ منابع APT میزبان را بازنویسی و بررسی امضا را غیرفعال نمی‌کند. روی نسخه‌های دیگر، خطای منابع اختصاصی میزبان باید توسط مالک سرور رفع شود.

پایتون پیش‌فرض سیستم عوض نمی‌شود؛ برنامه در venv خودش اجرا می‌شود. کتابخانه‌های تغییرنام‌یافتهٔ t64 از کاندید واقعی APT انتخاب می‌شوند. Chromium اوبونتو از توزیع ثابت Playwright 1.63.0 نصب می‌شود؛ نیاز به Snap یا PPA ندارد و فایل‌های نسخهٔ قبلی برای rollback باقی می‌مانند. در میزبان دارای محدودیت AppArmor، فقط مسیر root-owned مرورگر Donino اجازهٔ user namespace می‌گیرد. تست راه‌اندازی مرورگر با کاربر سرویس، قبل از فعال‌سازی انجام می‌شود.

ماتریس CI نصب تعاملی هر دو نقش، ارتقا، بوت systemd، جفت‌سازی HTTPS با ورود root در SSH غیرفعال، هر هشت حامل و rollback را برای نسخه‌های بالا به‌جز 26.10 اجرا می‌کند. یک تست جداگانه روی میزبان واقعی Ubuntu 22.04/24.04، Chromium و انتقال داده را با سیاست AppArmor میزبان بررسی می‌کند. این‌ها آزمایش WAN ایران یا همهٔ کرنل‌های VPS نیستند.

منابع: [انتشارهای Ubuntu](https://ubuntu.com/project/docs/release-team/list-of-releases/)، [زمان‌بندی 26.10](https://documentation.ubuntu.com/release-notes/26.10/schedule/)، [نصب مرورگر Playwright](https://playwright.dev/python/docs/browsers).

## جفت‌سازی از پنل

۱. وارد پنل خارج شو و «ساخت کد جفت‌سازی» را بزن.

۲. در پنل ایران «راه‌اندازی خودکار» را باز کن و نام اتصال، IP/دامنهٔ خارج، پورت agent و کد را وارد کن.

۳. «جفت‌سازی و آزمون مدیریت امن» را بزن. ایران اثر انگشت TLS خارج را **پیش از ارسال اطلاعات HTTP** از کد بررسی می‌کند. یک token اختصاصی می‌گیرد و نوشتن، خواندن و حذف فایل موقت در agent خارج را آزمایش می‌کند. نصب، کنترل سرویس و ویرایش مجاز از همین کانال HTTPS انجام می‌شوند؛ ورود root با SSH لازم نیست.

کد ۱۰ دقیقه معتبر و یک‌بارمصرف است. ساخت کد جدید قبلی را باطل می‌کند. اگر پاسخ جفت‌سازی گم شد، کد تازه بساز؛ این با بازیابی رسید عملیات نصب تفاوت دارد. کلید SSH یا مجوز ورود root جدیدی در جفت‌سازی HTTPS ساخته نمی‌شود. اتصال دستی SSH فقط برای سازگاری قدیمی باقی مانده و fallback پنهانی نیست.

در همان صفحه، «آزمون ارتباط و دریافت سرویس‌های خارج» را بزن. نتیجهٔ واقعی نوشتن/خواندن، آمادگی root/systemd و یکسان‌بودن runtime دو طرف نمایش داده می‌شود. پیش از ویرایش سرویس بیرونی، مدیریت همان سرویس را صریحاً فعال کن. اطلاعات بیشتر: [کانال مدیریت HTTPS](management.md).

اجازهٔ اولیه در پنل خارج همچنان لازم است: مالک سرور با ساخت کد مشخص می‌کند کدام ایران مجاز به مدیریت root خارج است. کشف و اعتماد خودکار به سرور دلخواه بدون این اجازه پیاده نشده است.

## ساخت تانل

در ایران پروتکل‌ها، ورودی TCP و مقصد loopback خارج را انتخاب کن. مثلاً ورودی `0.0.0.0:443` و مقصد `127.0.0.1:8443`. **برنامهٔ مقصد باید از قبل روی خارج فعال باشد**؛ پروژه خودِ سرویس VPN یا برنامهٔ دلخواه را نصب نمی‌کند.

نقشه را ببین، پورت‌ها و جایگزینی مجموعهٔ قبلی را بررسی کن و نصب را شروع کن. پیش‌نیازها و بسته‌های متناسب با حامل انتخاب‌شده روی هر نقش نصب می‌شوند. هر دو سرور پیش از فعال‌سازی آماده می‌شوند؛ سپس خارج و ایران فعال و تمام مسیرها آزمایش می‌شوند. کار با بستن مرورگر متوقف نمی‌شود. رمز، آدرس و credentialهای هر دو پنل در جایگزینی تانل‌ها حفظ می‌شوند؛ بعد از restart ممکن است دوباره ورود لازم باشد. [جزئیات نصب و rollback](panel-installer.md).

حامل‌های `donino-mux` و `donino-continuum` با انتخاب صریح آزمایشی در همین فرم نصب می‌شوند؛ Chromium نیاز ندارند. Continuum بازیابی نشست فعال روی WSS را با مهلت محدود دارد. [Mux v1](donino-mux.md) · [Continuum v2 و ارتقا](continuum.md).

## امکانات پنل خارج

- وضعیت واقعی systemd هر واحد: روشن/خاموش، RAM و تعداد restart.
- شروع، توقف و restart واحدهای متعلق به Donino؛ سرویس SSH یا سرویس‌های دلخواه میزبان در این API قابل کنترل نیستند. توقف واحد پنل/سلامت از داخل خودش نیز مسدود است؛ restart آن ممکن است نیازمند ورود دوباره باشد.
- آزمایش مستقل سرویس سلامت و تمام مقصدهای TCP و تاریخچهٔ نتیجهٔ عملیات.
- سلامت هر حامل بر پایهٔ آزمون رفت‌وبرگشت امضاشده از ایران و زمان آخرین گزارش.
- وضعیت «نامشخص» هنگام نبودن گزارش تازه؛ start شدن systemd به‌تنهایی موفقیت تانل محسوب نمی‌شود.
- شمارندهٔ واقعی جریان، آپلود و دانلود از relayهای همان سرور؛ دادهٔ قدیمی یا متعلق به PID قبلی پذیرفته نمی‌شود. نبود داده با «—» نمایش داده می‌شود. شمارنده‌ها با restart relay صفر می‌شوند و صورتحساب پایدار ترافیک نیستند.
- نمایش جفت‌های مجاز، ساخت کد تازه و لغو اجازهٔ مدیریت. لغو، کلید متعلق به آن جفت، token agent و آخرین گزارش سلامت همان جفت را باطل می‌کند؛ پنل در نوبت پایش بعدی وضعیت را «نامشخص» می‌کند. درخواست قدیمی اجازهٔ ثبت گزارش تازه پس از لغو ندارد. تانل‌های جاری متوقف نمی‌شوند.
- رابط فارسی RTL، روشن/تیره، موبایل، رویدادها و نمودار تأخیر.

نصب ایران یک lease زمان‌دار روی خارج می‌گیرد؛ عملیات سرویس، جفت‌سازی یا لغو در خارج نمی‌تواند هم‌زمان نصب را تغییر دهد. پنل خارج یا حامل‌ها می‌توانند restart شوند و agent مستقل باقی می‌ماند. پس از پایان یا بازیابی نصب، lease آزاد می‌شود؛ در صورت قطع ارتباط، حداکثر بعد از یک ساعت منقضی می‌شود.

## پیش‌نیازها و تنظیم منابع

ایران در نصب اولیه Python/venv، OpenSSL و SSH client و سرویس root کنترل را می‌گیرد. خارج agent مستقل TLS را می‌گیرد؛ نصب و پیکربندی SSH server دیگر پیش‌نیاز این مسیر نیست. Chromium/Node.js فقط برای نقش و حامل لازم نصب می‌شوند؛ همهٔ موتورهای آزمایشی در نصب اولیه دانلود نمی‌شوند.

واحدهای مدیریت‌شده حد فایل باز `65536`، restart محدود و خودکار، حافظه و تعداد task محدود و دسترسی فایل نوشتنی محصور دارند. SSH کنترل keepalive دارد و انتقال‌ها از backpressure و سقف جریان/بافر استفاده می‌کنند. تنظیم عمومی sysctl، خاموش‌کردن sandbox و تغییر سیاست کل فایروال به‌عنوان «بهینه‌سازی» انجام نمی‌شود؛ این تنظیمات محدود تضمین سرعت روی WAN نیستند.

## ارتقا و خطایابی

روی خارج و سپس ایران، در ترمینال root:

```bash
curl -fL --retry 3 --connect-timeout 15 https://raw.githubusercontent.com/danialrad04-sketch/donino-tunnel/main/install-donino.sh -o install-donino.sh && bash install-donino.sh --upgrade
```

نصب‌کنندهٔ ۰.۲.۰، پنل و runtime تانل‌های مدیریت‌شده را به‌روز می‌کند. Paqet و سرویس‌های مستقل فقط مشاهده می‌شوند و توسط این ارتقا restart یا بازنویسی نمی‌شوند. سرویس‌های مدیریت‌شدهٔ خود Donino از نو شروع می‌شوند و اتصال‌های جاری آن‌ها ممکن است قطع شوند. هر دو طرف باید نسخهٔ جدید داشته باشند؛ پس از ارتقا پنل را reload کن.

```bash
/opt/donino-link/current/venv/bin/python -c 'from donino_link import __version__; print(__version__)'
```

خروجی نسخه باید `0.2.0` باشد. روش جایگزین با نسخهٔ جدید پوشهٔ پروژه روی همان سرور:

```bash
sudo bash scripts/setup.sh --upgrade
```

نقش و آدرس فعلی خودکار خوانده می‌شوند. تنظیمات فعال، رمز و پورت موجود حفظ می‌شوند؛ تغییر نقش نصب موجود پذیرفته نمی‌شود. فرمان نصب تک‌خطی بالا نیز در نصب موجود منوی ارتقا می‌دهد. هنگام job یا عملیات سرویس فعال، ارتقا رد می‌شود. در شبکهٔ خصوصی VPC/LAN، فقط root ایران می‌تواند `--allow-private-peers` را هنگام نصب اضافه کند؛ پیش‌فرض فقط آدرس عمومی خارج پذیرفته می‌شود.

```bash
# ایران
sudo systemctl status donino-link donino-control
sudo journalctl -u donino-control -n 100 --no-pager
# خارج
sudo systemctl status donino-link donino-foreign-agent ssh
sudo journalctl -u donino-foreign-agent -n 100 --no-pager
```

کلیدها و tokenها root-only در `/var/lib/donino-control` و `/var/lib/donino-foreign` می‌مانند. فایل کلید SSH پروژه `/var/lib/donino-foreign/authorized_keys` است؛ کلیدهای اپراتور در `/root/.ssh/authorized_keys` دست‌نخورده می‌مانند. drop-in اختصاصی SSH فقط root از IP جفت‌شده را با کلید مجاز می‌کند؛ tokenهای agent نیز به IP واقعی همان اتصال محدودند. تغییر IP خروجی ایران نیازمند جفت‌سازی تازه است. دسترسی SSH این جفت برای نصب، **مجوز مدیریت root خارج** است، هرچند forwarding، PTY و agent forwarding روی کلید مسدودند.

HTTP پنل‌ها طبق انتخاب مدیر پشتیبانی می‌شود؛ اطلاعات ورود، نشست و کد داخل HTTP رمزنگاری نمی‌شوند. TLS پین‌شدهٔ agent این محدودیت پنل HTTP را تغییر نمی‌دهد. احراز هویت، CSRF، Origin check و rate limit فعال‌اند. برای نشانی خارج از `9444` در provider، تنظیم پورت واقعی و دسترسی مستقیم لازم است؛ reverse proxy عمومی پنل به‌صورت خودکار agent را proxy نمی‌کند.


برای مدیریت Paqet که با اسکریپت دیگری نصب کرده‌ای، [راهنمای تشخیص و پذیرش نصب فعلی](existing-paqet.md) را ببین. ارتقا با `sudo bash install-donino.sh --upgrade` نقش و نشانی فعلی را خودکار می‌خواند.
